User decision 2026-10-31. `MLXLanguageModel` sets `Memory.cacheLimit` once per process: 256 MiB originally (f1573a93), then 1/32 of the working set (fadf1b16, ^1abqd92). Both are arbitrary. MLX's allocator defaults `max_pool_size_` to `block_limit_`, and ChatSession never overrides it. Per-round churn is 0.6–2 GiB and grows with context, so no constant fits.

- [ ] Remove `configureGPUCacheOnce` and `gpuCacheLimitBytes(workingSetBytes:)` and their test (MLXLanguageModelGPUCacheLimitTests); an app can still set `Memory.cacheLimit` itself. Keep the GPU-built causal-mask positions.
- [ ] Check the history for why 256 MiB was chosen; if a real constraint turns up (iOS, host-app budget), record it on the card and raise it with the user rather than silently dropping it.
- [ ] Measure on the router path at 100k context: decode tok/s against the 1/32 limit, MLX active + cache memory, and peak process footprint.
- [ ] Prove the pool yields under pressure: with target + drafter + flash + embedder loaded (Router's JointFit set) confirm MLX releases cached buffers instead of growing past the budget. Report the numbers so foundationmodelsrouter-ce can account for them.
- [ ] Update the doc comments and any README mention.
