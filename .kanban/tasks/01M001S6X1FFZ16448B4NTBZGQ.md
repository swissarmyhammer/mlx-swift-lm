title: ToolCall arguments lose their order, thus a replayed DSML call cannot reproduce the model's own bytes
---
Found while working card `^2dvj1g6`.

`ToolCall.Function.arguments` is a `[String: JSONValue]`, and `ToolSpec` is a
`[String: any Sendable]`. Both are Swift dictionaries, which keep no order.

`DSMLToolCallParser` reads the `<｜DSML｜parameter>` elements of a call in the
order the model wrote them, and it puts them in that dictionary, which loses the
order at once. When `ChatSession` renders the same turn again as history,
`DeepSeekV4ChatEncoder` cannot write the parameters back in the order the model
wrote them.

Card `^2dvj1g6` made the write deterministic: `PythonStyleJSON` writes the
published member order for the names the published tool schemas use, and sorts
every other name. That removes the run-to-run noise. It cannot give the model's
own order back, and two places carry a real order the reference keeps:

- The members of a `properties` object. The published input
  `encoding/tests/test_input_3.json` writes `id, cursor, loc, num_lines,
  view_source`; a sort writes `cursor, id, loc, num_lines, view_source`.
- The arguments of one call.

## Why it matters

A round-2 prompt that writes round 1's tool call with the parameters in a
different order is not a prefix of what the model produced, thus
`ExtendCachedPrefixRule` cannot reuse the cache across a tool round. Card
`^mscrreq` measures that reuse.

## The work

- [x] Decide whether `ToolCall.Function.arguments` and `ToolSpec` take an
      ordered form. Both are public, thus the change reaches every tool-call
      parser, `Tool.swift` and the FoundationModels adapter
- [x] If they do, carry the order from `DSMLToolCallParser` through to
      `DeepSeekV4ChatEncoder` and prove it with a round trip: parse one DSML
      block, render it again, and compare the bytes
- [x] If they do not, record why on this card and close it

## The decision

`ToolCall.Function.arguments` and `ToolSpec` keep their type. The order goes
beside them, in a new member. The reasons:

- `arguments` is `public let arguments: [String: JSONValue]` on a
  `public struct ... Hashable, Codable, Sendable`. A change of its type breaks
  the public API, changes the `Codable` wire form, and changes the `Hashable`
  behaviour for every consumer.
- The blast radius is 15 files: 3 in `Libraries/` (`MLXLMCommon/Chat.swift`,
  `MLXFoundationModels/MLXLanguageModel.swift`,
  `IntegrationTestHelpers/IntegrationTestHelpers.swift`), 8 in `Tests/` and 4 in
  `IntegrationTesting/`.
- The codebase already solves this problem the additive way.
  `DeepSeekV4ChatEncoder.ToolCall` carries `public var argumentsJSON: String` —
  raw JSON text — and the encoder makes one DSML parameter for each member of
  that text, in the order of the text. Thus the encoder side already keeps the
  order. The break is only in the bridge that goes through
  `ToolCall.Function.arguments`.

## What the change adds

`ToolCall.Function` gets `public let argumentsJSON: String?`: the arguments as
the model itself wrote them, as JSON text.

- Raw JSON text, and not a list of names. The text keeps the order AND the
  digits of each number, because `PythonStyleJSON` holds a number as the text of
  the source. A list of names keeps only the order, and it needs a second lookup
  at each render. The text is also the form that
  `DeepSeekV4ChatEncoder.ToolCall.argumentsJSON` already takes, thus the bridge
  passes it through and converts nothing.
- The member is optional, and both initializers give it the default `nil`. Thus
  every caller that has no order keeps working, and the render falls back to the
  fixed order of `arguments`.
- The member takes NO part in equality. `==` and `hash(into:)` read the name and
  the arguments only. Two calls with the same name and the same arguments ask
  the same thing of the same tool; the text is one spelling of the same
  arguments, thus it must not split them. The two agree, thus the `Hashable`
  contract holds.
- `Codable` stays synthesized. An optional member encodes with
  `encodeIfPresent`, thus a call that carries no text writes the same bytes as
  before, and a decoder of the old form still reads the new form.

## The chain

1. `DSMLToolCallParser` reads the parameters in the order of the text and writes
   `argumentsJSON`.
2. `MessageGenerator.addToolMetadata(to:for:)` writes that text into the raw
   message dictionary, beside the `arguments` object, under the new key
   `ToolCall.Function.argumentsJSONKey` (`"arguments_json"`). The key is a new
   one, thus no template that reads `arguments` changes.
3. The DeepSeek-V4 bridge in `Chat.swift` reads `arguments_json` first, and the
   encoder writes one DSML parameter for each member of that text.

## The `properties` order

The other half of the order problem — the member order of a `properties` object
of a tool SCHEMA — is NOT part of this change. A schema comes in through
`ToolSpec`, which this card does not touch. That half needs work of its own.
