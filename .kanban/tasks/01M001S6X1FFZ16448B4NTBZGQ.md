title: ToolCall arguments lose their order, thus a replayed DSML call cannot reproduce the model's own bytes
---
Found while working card `^2dvj1g6`.

`ToolCall.Function.arguments` is a `[String: JSONValue]`, and `ToolSpec` is a
`[String: any Sendable]`. Both are Swift dictionaries, which keep no order.

`DSMLToolCallParser` reads the `<｜DSML｜parameter>` elements of a call in the
order the model wrote them, and it puts them in that dictionary, which loses the
order at once. When `ChatSession` renders the same turn again as history,
`DeepSeekV4ChatEncoder` cannot write the parameters back in the order the model
wrote them.

Card `^2dvj1g6` made the write deterministic: `PythonStyleJSON` writes the
published member order for the names the published tool schemas use, and sorts
every other name. That removes the run-to-run noise. It cannot give the model's
own order back, and two places carry a real order the reference keeps:

- The members of a `properties` object. The published input
  `encoding/tests/test_input_3.json` writes `id, cursor, loc, num_lines,
  view_source`; a sort writes `cursor, id, loc, num_lines, view_source`.
- The arguments of one call.

## Why it matters

A round-2 prompt that writes round 1's tool call with the parameters in a
different order is not a prefix of what the model produced, thus
`ExtendCachedPrefixRule` cannot reuse the cache across a tool round. Card
`^mscrreq` measures that reuse.

## The work

- [ ] Decide whether `ToolCall.Function.arguments` and `ToolSpec` take an
      ordered form. Both are public, thus the change reaches every tool-call
      parser, `Tool.swift` and the FoundationModels adapter
- [ ] If they do, carry the order from `DSMLToolCallParser` through to
      `DeepSeekV4ChatEncoder` and prove it with a round trip: parse one DSML
      block, render it again, and compare the bytes
- [ ] If they do not, record why on this card and close it
