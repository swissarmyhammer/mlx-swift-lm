## What

Research on 2026-10-12 (session scratchpad, Python sources in `dl/`) found per-step ops in our decode step that the Python ports do not run. Each one is small. Together they add about 1,000 kernels for each step.

1. **Masks on compressed layers at L=1.**
   - Ours: `DeepSeekV4Attention.swift:506-521, 638-651` makes ones, a broadcast, the chunk visibility and two concatenations on 41 layers, about 330 kernels.
   - mlx-lm PR 1195 (`deepseek_v4.py:1092-1093`) uses `mask=None` when S == 1, because every complete chunk is visible.
2. **Gate weight cast on each step.**
   - Ours: `DeepSeekV4MoE.swift:312` casts the BF16 gate weight `[256, 4096]` to float32 on each step, about 260 MB of traffic.
   - Python does the matmul in BF16 (`mlx_vlm .../language.py:147-167, 502`). Cast once at load, or match Python. Record the numeric decision.
3. **Query-head RMS norm.**
   - Ours: `DeepSeekV4Attention.swift:672-676` uses 8 float32 ops.
   - Python uses one `mx.fast.rms_norm(q, None, eps)` (`mlx_vlm .../language.py:850`).
   - Use `MLXFast.rmsNorm`.
4. **Sink cast.** `DeepSeekV4Attention.swift:478` casts the attention sinks on each step. Keep the cast result.
5. **Cache state placeholders.**
   - `TokenIterator.next()` evaluates `cache.flatMap { $0.state }` on each step (`Evaluate.swift`).
   - `DeepSeekV4ChunkCache.state` makes new `MLXArray([carryStart])` and `zeros([1])` placeholders on each call (`DeepSeekV4Cache.swift:124-135, 243`).
   - Make the per-step evaluation use arrays that are already there, for example `innerState()`.
   - Keep the fix of commit 8086fda: the cache state must be evaluated at the end of prefill.
6. **Optional, needs a decision:**
   - Fuse `wq_a` and `wkv` at load (`pr1195 deepseek_v4.py:940-942, 1022-1024`). Both are affine 4-bit, group 64, with the same input.
   - The float32 casts in the routed and shared combine (`DeepSeekV4MoE.swift:397-403`). Python combines in BF16. This changes numbers, so record the decision.
