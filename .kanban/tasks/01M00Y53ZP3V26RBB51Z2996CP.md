title: Consumer-visible input token usage is always zero, because the usage channel send is disabled
---
Reported by the `FoundationModelsRouter` and `FoundationModelsMultitool`
sessions, from two independent read paths, on 2026-08-14. Localized in this
repository the same day.

## What the consumers see

Surface 1, `FoundationModelsRouter`, reads `Usage` off a completed turn
(`LanguageModelSessionBackendTests.swift`), against Muse Glimmer:

- `:541` `turn1Usage.input.totalTokenCount > 0` — FAILED, on the FIRST turn
- `:563` `turn2Usage.input.cachedTokenCount > 0` — FAILED
- `:574` `abs(turn2Usage.input.cachedTokenCount - turn1ProcessedTokenCount) <= tolerance` — FAILED

Surface 2, `FoundationModelsMultitool`, reads
`SessionEvent.turnEnded(TokenUsage)` off the event stream:

```
tokens=TokenUsage(tokensIn: 0, tokensOut: 347, contextFill: 0.00264739990234375)
```

That turn made five tool calls and spliced a full discovery catalog, thus
the input was large. The output count of 347 is correct.

## The cause, and it is already written in the source

`Libraries/MLXFoundationModels/MLXLanguageModel.swift:721` `emitUsage` does
NOT send usage to the FoundationModels channel. It gives usage to the
`generationObserver` task-local alone, which only a test reads. The comment
at `:752` says the effect word for word:

> Effect: the framework does not receive our per-response usage event, so
> consumer-visible usage for these responses may be absent or zero. Tests
> still observe usage through `generationObserver` above.

The reason is an SDK symbol drift, recorded at `:729`. The FM-27 beta
`.swiftinterface` declares `Response.Action.updateUsage(input:output:metadata:)`
with three parameters. The shipping FoundationModels dylib exports the older
two-parameter `updateUsage(input:output:)`. Our call took the `metadata:`
default, thus the compiler bound the three-parameter symbol, which does not
exist at run time. Under chained fixups that aborts the process at image
load; under lazy binding it faults through null the moment the send runs.
A `dlsym` guard does not help, because the compiled reference alone is
enough to abort. Thus the send was removed.

## Why the input side alone looks wrong

This is the part the reports could not see, and it explains the asymmetry
exactly.

The framework counts the OUTPUT tokens itself, because it receives them.
Nobody but this repository can know the INPUT count, and this repository
does not send it. Thus:

- output — correct, and it comes from the framework, not from us
- input — zero, because no value ever arrives

Thus `tokensIn: 0` is not an input-specific defect. It is the whole usage
event that never arrives, and the output number hides that.

`contextFill` at 0.0026 is small and non-zero, thus the framework computes
it from something of its own.

Every one of the five `emitUsage` call sites also hard-codes
`cachedTokenCount: 0` (`:1423`, `:1642`, `:1732`, `:1781`, `:1974`). That is
a second defect under the first: even after the send is restored, the cached
count stays 0 and the two `cachedTokenCount` assertions above stay red.

## Open decision — a non-zero `cachedTokenCount` needs a feature

The premise of the fourth item does not hold in this repository. Measured on
2026-08-15:

- `Libraries/MLXFoundationModels/` holds NO prompt cache. A search for
  `KVCache`, `kvCache`, `cachedTokens`, `PromptCacheReuse` or `ChatSession`
  over that directory returns 0 matches.
- Each generation entry point the executor reaches takes the default
  `cache: nil`, thus `TokenIterator` builds new cache state for each request.
  `respond(to:model:streamingInto:)` renders the whole transcript again on
  each call. No token of an earlier turn is ever reused.
- `GenerateCompletionInfo` carries no reuse count. The reused count IS
  computed in `MLXLMCommon.PromptCacheReusePolicy`, but only `ChatSession`
  consumes it, and the value dies in that `switch`.
- `Evaluate.swift` names `MLXFoundationModels` `Executor.commitPromptCache`
  in a doc comment. That symbol does not exist in the tree.

Thus the true reused count is exactly ZERO at all five call sites today. The
five sites now carry that measured zero through the named, documented
`Executor.reusedPromptTokenCount`, rather than an unexplained literal.

A non-zero count needs cross-turn prompt-cache reuse inside the executor.
That is a feature, not a value to thread, and it is what the two red
`cachedTokenCount` assertions of `FoundationModelsRouter` really ask for.
The user decides whether this card grows to carry that feature, or whether a
new card carries it.
